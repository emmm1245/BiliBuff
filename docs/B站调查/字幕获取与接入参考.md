# 字幕获取与接入参考

2026-10-16实现更新：本扩展现已独立实现视频助手，字幕后台读取位于 [video-api.ts【视频与字幕读取服务】](../../extension/src/video-api.ts)，工作台协调位于 [video-reading.ts【分P切换与页面任务管理】](../../extension/src/video-reading.ts)。通过浏览器只读复核当前样本，播放器信息接口返回 AI 中文字幕轨道，取得273句字幕；本次没有复制上游实现。下文保留原调查范围，使用方式见[视频助手](../使用指南/AI服务与计划分析.md#视频助手)。

[文档目录](../README.md)

**Bilibili-Evolved【B站增强脚本】通过“播放器信息接口返回字幕列表，再请求所选字幕地址”获取已有字幕。AI 自动字幕和普通上传字幕共用这条链路，不需要下载音视频或调用语音识别。**

本文用于后续在 BiliBuff 中接入字幕读取。调查日期为 2026-10-16；依据是上游源码及项目讨论，未通过 CDP【浏览器调试协议】操作浏览器，也未对 B 站接口发送实测请求。因此，下文确认的是该版本的实现，不能把它当作当前所有视频均可成功获取的保证。

源码固定在 [fa06dcec095d【本次分析的提交版本】](https://github.com/the1812/Bilibili-Evolved/commit/fa06dcec095dbccaba82f50ae2318c8d61c26671)，提交时间为 2026-09-26。以后复查优先对照文末的固定版本链接，避免主分支变化导致结论和源码错位。

## 获取流程

1. 确定当前视频的 aid【稿件数字编号】和 cid【当前分P的内容编号】。
2. 携带浏览器登录状态，请求播放器信息接口。
3. 从响应中取出字幕轨道列表，每条轨道包含语言、AI 标记及字幕正文地址。
4. 按用户选择的语言挑选一条轨道，再请求其正文地址。
5. 从正文响应取出带起止时间的文本片段；按需保存原始数据或转换成带样式的字幕文件。

可按下面的顺序理解数据依赖：

> 视频与分P编号 → 播放器信息 → 字幕轨道列表 → 选定轨道的正文地址 → 带时间戳的文本 → 展示、分析或导出

源码入口是 [下载组件注册][subtitle-entry]；[语言选择界面][subtitle-ui]负责列出选项，[字幕请求与导出实现][subtitle-utils]负责实际获取。

## 两次请求分别取什么

### 请求字幕列表

实际请求地址为：

```text
GET https://api.bilibili.com/x/player/wbi/v2?aid=<稿件数字编号>&cid=<当前分P内容编号>
```

GET【只读请求】中的两个编号都必须存在。getSubtitleList【获取字幕列表】调用 getJsonWithCredentials【携带浏览器身份请求结构化数据】，再交给 bilibiliApi【检查B站业务状态并取出数据】处理响应。

| 项目 | 该版本源码行为 |
| --- | --- |
| 请求参数 | 只在地址上拼接 aid【稿件编号】和 cid【分P编号】 |
| 登录状态 | 底层 XMLHttpRequest【浏览器网络请求对象】设置 withCredentials=true【允许携带跨域请求凭据】，由浏览器附带适用的登录信息 |
| 成功判定 | 响应 code【业务状态码】必须为 0；非 0 抛出错误 |
| 数据入口 | 完整响应中的 data.subtitle.subtitles【字幕轨道数组】；业务封装先取出 data【业务数据】，字幕函数再读取内部路径 |
| 空列表 | 路径不存在时按空数组处理；下载函数随后提示当前视频没有字幕，并返回空结果 |
| 签名 | 这条调用链没有获取签名密钥，也没有自行添加 w_rid【请求签名】或 wts【签名时间戳】 |

**接口路径带 wbi【B站接口签名体系名称】，不等于这段代码实现了签名。** [字幕函数][subtitle-utils]和[底层请求封装][ajax]均未在此请求中追加签名。这只能说明上游这样调用，不能据此认定服务器在所有环境下都不校验签名。接入时先验证这条最小请求，出现明确的签名要求后再处理。

登录方面，上游复用现有浏览器会话，没有要求用户把 Cookie【浏览器保存的登录信息】复制给程序，也没有在这条链路中读取并保存其值。社区接口资料说明，未登录可能得到空字幕列表；因此后续界面不能把一次空返回直接解释为“这个视频永远没有字幕”。参见[播放器接口资料][player-api-doc]。

### 请求字幕正文

getSubtitleBlob【获取字幕并生成导出文件】选中轨道后，直接把 subtitle_url【字幕正文地址】交给 getJson【普通结构化数据请求】。这次没有使用前面的携带跨域凭据版本，代码也不自行拼接字幕文件路径。

| 数据层级 | 内容与用途 |
| --- | --- |
| subtitle_url【正文地址】 | 从接口返回的轨道中取得，保留完整路径和查询参数 |
| body【字幕片段数组】 | 正文响应中的实际字幕内容 |
| from【开始时间】 | 片段开始的秒数，可有小数 |
| to【结束时间】 | 片段结束的秒数，可有小数 |
| content【文本内容】 | 一段字幕文字 |
| location【位置字段】 | 上游片段类型中还声明了此字段；内容分析通常不需要它 |

这里的字幕不是弹幕，也不是播放器画面上的文字截图。该函数一次读取正文响应中的整个数组，没有在此实现字幕正文分页。

项目[历史讨论][ai-discussion]给出的字幕地址同时包含普通字幕路径和 AI 字幕路径。**不要通过域名中是否出现 AI、是否有文件扩展名来区分字幕类型，也不要根据编号猜正文地址。** 返回地址可能以双斜线开头；网页请求会沿用当前协议，扩展后台接入时应显式转换成完整的 HTTPS【加密网络协议】地址，并保留查询参数。

## 视频编号从哪里来

### 在已打开的视频页下载

getSubtitleBlob【获取并导出字幕】允许调用方传入编号；没有传入时，使用 unsafeWindow.aid【页面环境中的稿件编号】和 unsafeWindow.cid【页面环境中的当前分P编号】。缺少任一编号直接报错。

unsafeWindow【上游脚本访问页面执行环境的入口】不是浏览器扩展内容脚本天然拥有的变量。后续不能把这两行照搬进扩展，就假定能够读到页面全局对象。

### 从视频链接获取编号

上游另有 [VideoInfo【视频详情读取类】][video-info]，通过视频详情接口取得稿件编号、内容编号和分P信息：

```text
GET https://api.bilibili.com/x/web-interface/view?bvid=<视频BV编号>
```

这是上游的视频信息工具提供的能力，不是下载字幕组件每次自动执行的前置请求。该类的 fetchInfo【获取视频详情】会读取返回的 aid【稿件编号】、cid【默认内容编号】等信息；分P数据中也有各自的 cid【该分P内容编号】和 pageNumber【分P顺序号】。

后续只掌握 BV 编号时，可以先查询详情，再选择目标分P；不能用第一页的内容编号读取整个多P视频。也不要使用该类旧的 subtitles【已废弃的字幕属性】，该版本这个属性只会警告并返回空数组。

## AI字幕和普通字幕如何选择

### 界面会保留两种轨道

SubtitleInfo【字幕轨道信息】声明了以下关键字段：

| 字段 | 用途及源码实际使用方式 |
| --- | --- |
| lan【语言代码】 | 选择字幕的匹配键，例如 ai-zh【AI中文字幕的常见语言代码】 |
| lan_doc【语言显示名称】 | 下拉菜单展示给用户的名称 |
| subtitle_url【正文地址】 | 获取所选轨道内容 |
| ai_status【AI字幕状态值】 | 界面判断其不为 0 时，在名称后追加 AI 标记 |
| ai_type【AI类型值】、type【轨道类型值】 | 类型中有声明；此下载链路没有按这两个字段筛除字幕 |
| id_str【字符串形式的字幕编号】 | 用于按大整数排序语言选项，避免把超长编号当普通数字比较 |
| id【数字形式编号】、is_lock【锁定标志】 | 类型中有声明；此处没有用它们决定是否下载 |

[语言选择界面][subtitle-ui]没有排除 AI 轨道，也没有在获取正文时对两类字幕走不同接口。它按字幕编号排序后生成语言选项，并用 AI 状态值添加显示标记。**这是该项目的界面判定规则，不应把单个字段的值扩大解释为完整的B站字幕分类协议。**

### 实际下载的优先顺序

[字幕获取函数][subtitle-utils]按下面的顺序选一条轨道：

1. 调用方明确传入 language【指定字幕语言】时，用它匹配 lan【轨道语言代码】。
2. 没有明确指定时，用播放器保存的字幕语言偏好匹配。
3. 匹配失败，选择接口原始列表的第一条轨道。

函数没有实现“优先人工字幕”或“优先中文字幕”的策略，也不会自动把所有语言都下载下来。**界面选项经过排序，但最后的兜底来自接口原始列表；不能把它理解为固定选择界面上的第一项。**

播放器偏好通过 [getPlayerConfig【读取播放器本地配置】][player-config]取得：新版主要读取 bpx_player_profile【新版播放器本地配置键】，兼容分支读取 bilibili_player_settings【旧播放器本地配置键】，再取其中的 subtitle.lan【保存的字幕语言】。这份配置主要影响默认选项及导出样式，字幕正文来自网络接口。

项目[历史讨论][ai-discussion]指出，播放器切换到 AI 字幕时，保存的语言值曾经不同步；依赖播放器私有对象获取当前选择也曾因更新失效。当前版本提供独立语言下拉菜单，用户选择会传给下载函数。因此后续若需要确定读取哪种字幕，应明确选择轨道，不把本地偏好当成当前字幕显示状态的可靠证明。

## 获取后的处理与实现边界

### 导出格式

该组件的 SubtitleDownloadType【可选导出格式】只有两种：

| 格式 | 实际输出 |
| --- | --- |
| JSON【结构化数据文件】 | 仅保存 body【字幕片段数组】，不是包含所有顶层字段的完整正文响应 |
| ASS【带样式的字幕文件】 | 将片段起止时间和正文转换成字幕条目，并应用字体、位置、颜色等设置 |

[格式转换器][subtitle-converter]处理字幕样式与时间格式，[下载工具][download-core]将内容生成内存文件地址，再触发浏览器下载。这是本地转换与保存，未额外调用字幕生成服务。这个组件没有提供 SRT【常用时间轴字幕格式】或 TXT【纯文本格式】导出。

**如果我们只需要阅读、摘要或模型分析，取得片段数组后即可使用，不必引入整套字幕样式转换和文件下载代码。**

### 与播放器的耦合

getSubtitleBlob【获取并导出字幕】在拿到列表后，总会调用 getSubtitleConfig【读取字幕样式与语言偏好】；存在字幕设置时，后者还会访问视频元素的画面宽高。即使选择结构化数据导出，也会经过这一步。

因此，“两个网络请求能拿到字幕”不代表“上游完整导出函数能直接在首页或后台运行”。后续应独立保留“读取列表、选择轨道、读取正文”这条数据流程，把页面样式和视频元素访问留给确有需要的导出功能。

### 批量入口与覆盖范围

[组件注册文件][subtitle-entry]还把下载字幕作为视频下载功能的附加资源。批量入口对每个输入视频分别获取字幕，使用 Promise.allSettled【等待各任务完成并分别记录成败】汇总结果。无字幕时按失败记录，不生成成功的空条目；批量函数本身没有在这里设置并发上限。

[适用页面配置][page-urls]包含普通视频、部分列表播放页和番剧播放页，未把独立课程页面纳入这个组件的匹配范围。页面匹配表示允许组件出现，不代表源码分析已证明每一种付费或受限内容都能获取。

### 失败结果如何理解

| 表现 | 源码可确认的含义与后续判断 |
| --- | --- |
| 缺少视频编号 | 直接抛错；先解决稿件和分P身份，不继续请求 |
| 接口返回非零业务状态 | 业务封装抛错，不等同于无字幕 |
| 字幕列表为空或字段缺失 | 上游提示无字幕；仍需结合登录与接口兼容性判断 |
| 找不到指定语言 | 上游回退到第一条轨道；后续应让用户知道最终采用的语言 |
| 正文请求失败 | 请求链路报错，没有音频下载或语音转写作为补救 |
| 视频只有压在画面里的文字 | 这条字幕轨道读取流程不包含画面文字识别 |

在所分析的字幕调用链中，没有看到 /x/v2/subtitle/web/view【另一套字幕元数据接口】的后备请求，也没有 Protobuf【二进制结构化数据格式】解码。它们不能写成这个组件已经具有的能力。若未来遇到“播放器有字幕、旧接口列表为空”，应先区分登录、分P和接口变化，再针对实际缺口调查，不直接将空列表视为最终结论。

## 本扩展后续接入建议

以下是根据上述源码与本仓库现状提出的接入方向，本次仅整理文档，未实现字幕功能。

1. **先做按需读取单个视频。** 已知 BV 编号时查询详情，确定目标分P，再获取轨道及正文。具备两个编号后，最小数据流程是一次列表请求和一次正文请求；上游界面初始化与真正下载会分别请求列表，后续不必照搬这次重复获取。
2. **用后台处理跨域网络请求。** 本仓库 [comment-service.ts【评论后台读取服务】](../../extension/src/comment-service.ts)已有携带浏览器登录状态的请求方式，可参考职责划分；不要直接复用带评论专属提示、缓存和限流状态的整套服务。
3. **补齐正文域名权限。** [wxt.config.ts【扩展配置】](../../extension/wxt.config.ts)已有B站接口域名权限，但没有为常见的 aisubtitle.hdslb.com【字幕正文资源域名】声明专用权限。若采用后台读取，应按实际返回域名补充有限权限；现有“任意站点可选权限”不代表已经授权。后台根据受控视频编号查询轨道，不向页面暴露可请求任意网址的通用转发入口。依据见 [Chrome跨域请求说明][chrome-network]。
4. **字幕数据保留来源与时间轴。** 将视频编号、分P编号、最终语言、AI 标记和片段数组一起传给后续功能。是否优先人工字幕，需要结合产品需求明确，不能继承上游的“找不到就取第一条”而不显示结果。
5. **分清字幕缺失与请求失败。** 初版不自动下载音视频或引入语音识别。若接口不兼容，保留可识别的状态，后续按证据补充接口适配。

跨域资源读取能力由扩展权限和执行环境共同决定。Chrome【浏览器】官方说明，内容脚本仍受页面跨域规则约束；具有相应站点权限的扩展后台可发起跨域请求。上游项目的请求方式需要按扩展执行环境单独验证。

### 接入时的验证目标

| 场景 | 应检查的结果 |
| --- | --- |
| 只有普通上传字幕 | 读取到实际文本，标记与所选轨道一致 |
| 只有 AI 字幕 | 能选中并读取 AI 轨道，不误判为无字幕 |
| 同时有普通与 AI 字幕 | 指定语言后正文对应正确，不受旧本地偏好影响 |
| 多P视频切换分P | 使用对应内容编号，旧分P结果不覆盖新结果 |
| 未登录或视频确实无字幕 | 提示能区分登录问题、空列表与网络失败 |
| 正文地址以双斜线开头或带查询参数 | 后台使用完整加密地址，保留必要参数并有对应权限 |
| 无视频元素的后台读取 | 读取数据不依赖播放器尺寸和字幕样式 |
| 接口列表为空但播放器有字幕 | 保留接口兼容性问题线索，不宣称永久无字幕 |
