## 评论区从页面加载到显示

### 评论对象与延迟加载

视频页的外层容器为 `#commentapp`【评论区域挂载点】，内部挂载 `bili-comments`【B站评论区自定义组件】。本轮进入调查时页面还显示“正在玩命加载”，将评论区域滚入视口后才出现评论请求和内部列表。

组件属性 `data-params`【评论类型与评论对象编号】的实际值为 `1,117434052773600`；`lazy-load`【延迟加载开关】为 `true`【开启】。

本视频的 `aid`【稿件数字编号】与请求中的 `oid`【评论对象编号】一致。请求的 `type=1`【视频评论类型】。不要把 BV 编号或 `cid`【视频分P内容编号】直接填进评论对象参数。页面的 `window.__INITIAL_STATE__`【页面初始化数据】也包含本视频稿件编号，但扩展接入时优先读取已存在的组件属性，不必为取得编号额外访问页面脚本变量。

### 页面节点分层

本轮评论组件使用开放的 Shadow DOM【与外部页面分隔的内部节点树】，实际读取到的 `shadowRoot.mode`【节点树开放状态】为 `open`【允许脚本访问】。下表的每一级内部节点都需要先进入所属组件的 `shadowRoot`【内部节点树入口】，普通的文档选择器不会自动穿过它们。

| 层级与组件 | 职责和已见内部节点 |
| --- | --- |
| `bili-comments`【评论区总组件】 | 包含 `#header`【头部区域】、`#feed`【主评论列表】、`#continuations`【继续加载区域】 |
| `bili-comments-header-renderer`【评论头部组件】 | 总数、最热和最新切换，以及评论输入区域 |
| `bili-comment-thread-renderer`【一个完整评论楼层】 | 组合本楼主评论与回复列表 |
| `bili-comment-renderer`【主评论组件】 | 用户信息、正文、图片和操作栏 |
| `bili-comment-replies-renderer`【楼中楼列表组件】 | 初始预览、点击查看、页码、下一页与收起 |
| `bili-comment-reply-renderer`【一条楼中楼回复】 | 回复者、被回复关系、正文和操作栏 |
| `bili-rich-text`【评论富文本组件】 | 实际正文位于内部的 `#contents`【正文节点】 |

这会影响后续插件的评论隐藏、标记和按钮插入：既要发现新楼层，也要处理回复翻页后被替换的节点。`MutationObserver`【页面节点变化监听器】应观察相应的内部节点树，仅监听整个文档不能覆盖内部变更。开放节点树的访问规则见 [MDN 节点树入口说明](https://developer.mozilla.org/en-US/docs/Web/API/Element/shadowRoot)。

调试过程中可以通过组件的 `list`【已加载评论数据】、楼层的 `data`【本楼评论对象】读取数据，并调用 `getList()`【站点内部继续加载方法】验证真实请求。**这些是站点内部实现，且本次在页面执行环境中调用；不能直接当成扩展可用的稳定接口。**

## 主评论接口与排序

### 实际请求

主评论读取使用 [主评论接口](https://api.bilibili.com/x/v2/reply/wbi/main)，请求方式为 GET【只读请求】。

| 参数 | 本轮取值与用途 |
| --- | --- |
| `oid`【评论对象编号】 | 117434052773600 |
| `type`【评论类型】 | 1，视频评论 |
| `mode`【主列表排序方式】 | 3 为最热，2 为最新；由实际切换请求确认 |
| `pagination_str`【序列化后的翻页参数】 | 初次为包含空 `offset`【翻页游标】的对象；后续原样传回服务端给出的游标 |
| `plat`【客户端平台参数】 | 1 |
| `seek_rpid`【需要定位的评论编号】 | 本轮首批请求为空，后续不带；不用于全量遍历 |
| `web_location`【站点来源位置参数】 | 主列表为 1315875 |
| `w_rid`【WBI请求签名】、`wts`【签名时间戳】 | 原站主列表请求实际携带，由站点请求层生成 |

请求还出现了语言等环境参数。它们不替代评论对象、排序或游标。本轮没有逐一验证省略这些附加参数后的兼容性，也没有测试主评论接口能否省略签名。

当前站点脚本在调用接口时接入 WBI【B站请求签名机制】，并配置签名所需的公开密钥信息。后续直接构造请求时，应单独解决签名及更新来源；不要把本轮的一次性签名地址或脚本中的密钥值固定写进扩展。

### 响应中的关键位置

| 字段 | 作用与使用方式 |
| --- | --- |
| `code`【业务状态码】 | 本轮成功均为 0；网络成功不等于业务成功 |
| `data.replies`【本批主评论】 | 本轮每个常规批次最多返回 20 条；这只是本轮观察到的批量大小 |
| `data.top_replies`【独立返回的置顶评论】 | 本轮含 1 条UP主置顶；必须纳入并按评论编号去重 |
| `data.top`【分类保存的置顶信息】 | 本轮也包含同一条UP主置顶，不应再重复计数 |
| `data.cursor.all_count`【评论区显示总数】 | 本轮为 144，包含主评论和可见楼中楼回复 |
| `data.cursor.is_end`【当前遍历是否结束】 | 主列表完成遍历的主要依据 |
| `data.cursor.pagination_reply.next_offset`【下一批使用的游标】 | 包装回请求中的翻页参数，不能自行加一或按页码推导 |
| `data.cursor.session_id`【列表会话标识】 | 最热遍历中保持一致；不要把某次会话的游标当成永久页地址 |
| `data.control`【评论区展示与输入控制】 | 包含是否精选、是否禁用输入、提示文案等控制信息 |

当前组件在首批把置顶评论插入主列表，再按评论编号去重；同时跳过 `invisible`【不可见标记】为真的条目。最新排序切换后会清空已有列表，重新从首批开始。本轮除置顶外，最新列表按 `ctime`【发布时间秒级时间戳】倒序；置顶不参与这一时间顺序。

### 最热游标重复仍能返回下一批

这是本轮最容易导致漏采的发现。最热列表的前三批响应给出了**完全相同的下一批游标**，请求第二批和第三批时也发送了同一游标，但分别获得不同评论。第四批才返回空列表和结束标记；这几批的 `session_id`【列表会话标识】相同。

| 排序 | 批次 | 新增主评论 | 累计去重主评论 | 结束标记 |
| --- | --- | ---: | ---: | --- |
| 最新 | 1 | 20＋1条置顶 | 21 | 否 |
| 最新 | 2 | 20 | 41 | 否 |
| 最新 | 3 | 11 | 52 | 是 |
| 最热 | 1 | 20＋1条置顶 | 21 | 否 |
| 最热 | 2 | 20 | 41 | 否 |
| 最热 | 3 | 11 | 52 | 否 |
| 最热 | 4 | 0 | 52 | 是 |

因此，**游标未改变、返回数量不足 20、或者已达到页面总数，都不能单独用作主列表结束条件。** 最热第三批只有 11 条，也仍需继续读取结束状态。最热响应的 `is_begin`【是否为开头的标记】在这些批次中一直为真，同样不能用它判断实际批次。

这说明最热遍历至少表现出会话状态行为，不能假设“同一参数必定返回同一页”；服务端如何保存进度未确认。正式采集优先采用本轮能正常逐批推进的最新排序，保持一个连续任务，主列表串行请求。若未结束却连续无新增，应记录采集中断，不能伪报完成。

## 楼中楼接口与回复关系

### 预览不是本楼全部回复

主评论对象内的 `replies`【附带回复预览】只是一部分回复。本轮最新列表的 52 条主评论合计附带 32 条预览，而完整楼中楼实际有 92 条；直接合并主列表及预览只能得到 84 条评论，会漏掉 60 条。

页面点击“共若干条回复，点击查看”后发起新的请求。对超过一页的楼层，页面显示页码、下一页和收起。实测打开一个 13 条回复的楼层，第一页显示 10 条，第二页为 3 条。翻页会替换当前回复列表；收起则恢复展开前缓存的预览，不代表删除了已存在的回复。

### 独立分页参数

楼中楼读取使用 [楼中楼接口](https://api.bilibili.com/x/v2/reply/reply)，请求方式为 GET【只读请求】。

| 参数 | 用途 |
| --- | --- |
| `oid`【评论对象编号】、`type`【评论类型】 | 与主列表相同 |
| `root`【本楼主评论编号】 | 每次针对一条主评论，不能填本页序号 |
| `ps`【每页回复数量】 | 本轮原站和独立验证均使用 10；未测试其他值的上限 |
| `pn`【回复页码】 | 从 1 开始逐页增加 |

原站请求还携带来源、语言和设备参数。本轮独立验证仅发送表中五个参数，并让浏览器携带现有登录态，25 个回复页均成功返回，无需额外提供主列表使用的签名参数。这不等于证明未登录也可以全量读取。

| 响应字段 | 用途 |
| --- | --- |
| `data.page.num`【返回页码】 | 核对是否为请求页 |
| `data.page.size`【返回的页容量】 | 本轮为 10 |
| `data.page.count`【本楼当前可返回的回复总数】 | 本楼分页总量依据 |
| `data.replies`【本页回复】 | 保存并按评论编号去重 |
| `data.root`【本楼主评论信息】 | 用于核对归属，不再当作新增评论计数 |

例如本轮有一个楼层为 20 条回复，实际读取两页，每页 10 条。应结合本楼总数确定页数；不能只依赖“最后一页不足 10 条”。采集中若总数变化，应记录变化并重新核对，不能把空页或请求失败直接当作成功结束。

### 评论在存储上有两层 回复关系可以有多级

主评论的 `root_str`【所属主楼编号字符串】和 `parent_str`【直接被回复评论编号字符串】均为 `0`【没有上级】。楼中楼回复共享本楼主评论编号，但直接回复对象既可能是主评论，也可能是另一条楼中楼回复。

本轮实际观察到：主评论 → 回复A → 回复B → 回复C。它们仍然通过同一个楼中楼分页接口返回，不需要为每条回复递归请求一个新的列表。

| 字段 | 表达的关系 |
| --- | --- |
| `rpid_str`【本条评论编号字符串】 | 去重及关联的主键 |
| `root_str`【所属主楼编号字符串】 | 把回复归入对应楼层 |
| `parent_str`【直接被回复评论编号字符串】 | 还原多级回复关系 |
| `dialog_str`【所属对话分组编号字符串】 | 同一楼内某段对话的分组；不能替代直接父评论关系 |

本轮有 1 条回复的直接父评论没有出现在全部 144 条结果中：回复 317144722673 指向父评论 320792475152，所属主楼为 317080667505。具体不可见原因没有返回，不能断言一定被删除。保存这条回复及原始父编号即可，展示时允许父评论缺失，不应丢弃回复或无限追查。

## 计数 正文与可保留字段

### 两种回复计数不能混用

主评论同时带有 `count`【原始回复计数，其完整统计口径未确认】和 `rcount`【本轮与页面及回复分页一致的可见回复计数】。两者在 8 个楼层上不同。

| 主评论编号 | 原始计数 | 可见计数 | 回复接口实际返回 |
| --- | ---: | ---: | ---: |
| 317080667505 | 15 | 13 | 13 |
| 317030517377 | 22 | 20 | 20 |
| 320667465776 | 1 | 0 | 最新列表没有附带可见回复，本轮未单独请求此楼 |
| 全部52个楼层合计 | 104 | 92 | 完整读取有可见回复的21个楼层，共92条 |

不能为了凑齐较大的原始计数而不断翻页，也不能把两者的差值直接解释成“已删除数量”。本轮完成判定依据为主列表明确结束、逐楼可见计数与实际回复分页一致，以及全局去重总数核对。

### 正文与附加内容

后续最小数据集应保留评论编号、所属视频、主楼编号、直接父编号、正文、发布时间，以及所需的展示信息。编号优先使用接口提供的字符串形式，不依赖数字转换。

| 字段 | 内容与取舍 |
| --- | --- |
| `content.message`【评论原始正文】 | 用于文本分析与检索，避免只读取页面当前可见行；本轮最长正文745个字符 |
| `ctime`【发布时间秒级时间戳】 | 排序及显示时间 |
| `like`【当前点赞数】 | 展示或后续排序；会随时间变化 |
| `member.mid`【作者编号】、`member.uname`【作者昵称】 | 按功能需要保留；不用整包保存头像装饰、会员等无关信息 |
| `content.emote`【表情词与表情信息映射】 | 本轮实际出现，保留有助于还原表情 |
| `content.at_name_to_mid_str`【提及昵称与账号编号的映射】 | 本轮实际出现；正文中的提及不替代父评论关系 |
| `content.jump_url`【正文跳转链接信息】 | 本轮字段存在，是否保留取决于展示需求 |
| `reply_control`【本条评论的展示控制】 | 含置顶、回复入口文字、时间提示等，按实际功能选取 |
| `content.max_line`【页面默认展开行数限制】 | 属于展示限制，不应当成正文长度上限 |
| `content.pictures`【评论附图】 | 当前站点脚本支持，本轮样本未出现，尚未实测图片评论 |
| `reply_control.fold_pictures`【图片折叠控制】 | 当前脚本据此决定是否展示附图，尚未实测触发情况 |

接口中的文本、链接和图片信息均是内容数据，后续渲染时按文本和明确支持的富文本规则处理。无需把整份账号资料或网络请求头存入评论数据。
